## Objetivo

Deixar a VDI com Docker Engine e o plugin Compose v2, para que ela construa e publique as imagens. A instalação tenta primeiro os pacotes da distribuição, depois o repositório oficial da Docker e, por último, o binário standalone do Compose; a evidência registra qual caminho funcionou.

## Comandos

```bash
sudo_run bash ~/atividade3/payload4/install-docker.sh
sudo_run usermod -aG docker $(id -un)
getent group docker
sg docker -c 'docker version'
sg docker -c 'docker compose version'
```

## O que aconteceu

O Docker já estava instalado na VDI. O instalador é idempotente e saiu pelo caminho "já instalados": reabilitou o serviço, adicionou o usuário `osboxes` ao grupo `docker` e não baixou pacote nenhum. As versões são Engine `24.0.5` (cliente e servidor) e Compose `v2.20.2`, com driver `overlay2` e root em `/var/lib/docker`, sobre `/dev/sda2` com 210 GB livres.

## Decisões

Usar `sg docker -c` em vez de exigir um novo login: o grupo aplicado por `usermod` só vale para sessões novas, e `sg` consulta a base de grupos na hora, então o efeito é imediato dentro da automação. O instalador foi corrigido para aplicar o grupo também quando não há nada a instalar.

## Problemas

A primeira execução da fase travou: o instalador saía antes de incluir o usuário no grupo `docker`, o `sg` seguinte pedia senha e o `run.py` não encaminha stdin para responder. Correção: o caminho "já instalado" passou a executar `systemctl enable --now docker` e o `usermod`, e a fase ganhou uma chamada explícita de `usermod` antes de qualquer `sg docker`.
