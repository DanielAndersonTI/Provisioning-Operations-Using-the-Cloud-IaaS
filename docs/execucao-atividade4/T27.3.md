# T27.3 — Teste de failover de um container

| Campo | Valor |
| --- | --- |
| Data | 09/11/2026, 23:07 a 23:09; reexecutado em 10/11/2026, 00:29 a 00:31 (local); evidências em UTC |
| Fase | Fase 27 |
| Status | concluída |
| Evidências | `T27.3-stop`, `T27.3-member-degraded`, `T27.3-restore`, `T27.3-member-restored` |

## Objetivo

Parar o container de CPU, observar o membro do pool como `ERROR` e a VIP devolvendo `503`, subir de novo e confirmar a recuperação.

## Comandos

```bash
sudo docker compose --env-file /etc/poi-atividade4/docker.env stop cpu
sleep 45   # monitor HTTP: delay 5 s x max-retries 3
openstack loadbalancer member list pool-app-cpu-daniel-ranya
curl http://150.165.85.77:8100/health
sudo docker compose --env-file /etc/poi-atividade4/docker.env start cpu
sleep 45
openstack loadbalancer member list pool-app-cpu-daniel-ranya
curl http://150.165.85.77:8100/health
```

## O que aconteceu

O container `cpu` foi parado às 02:07:00 UTC; aos 02:07:57 o membro estava `ERROR` e a VIP devolvia `503` — o mesmo comportamento observado na Atividade 3 com `systemctl stop`. O container foi iniciado às 02:08:12 e, aos 02:09:04, o membro voltou a `ONLINE` e a VIP respondeu `200` em 0,047 s. A indisponibilidade medida foi de aproximadamente 1 minuto, compatível com o monitor do Octavia.

## Saída

```text
 Container poi-atividade4-cpu-1  Stopped

| vm-daniel-ranya | ERROR |
GET /health pela VIP -> HTTP 503

| vm-daniel-ranya | ONLINE |
{"status": "ok", "profile": "cpu"} HTTP 200 em 0.046566s
```

## Decisões

Usar `compose stop`/`start` em vez de matar o processo: reproduz a queda do serviço sem derrubar a VM e mantém o teste restrito ao perfil de CPU. Como `stop` é uma parada manual, a política `unless-stopped` não reiniciou o container — o teste mediu indisponibilidade real, e não uma recuperação automática.

## Problemas

Nenhum.
