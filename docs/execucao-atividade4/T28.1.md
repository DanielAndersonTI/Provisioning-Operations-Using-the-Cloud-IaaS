## Objetivo

Registrar o estado da VM com as três aplicações em containers e criar um snapshot do disco, para que o estado implantado possa ser recuperado sem repetir o deploy.

## Comandos

```bash
openstack server show vm-daniel-ranya -c name -c status -c addresses -c flavor -c image
sudo docker compose --env-file /etc/poi-atividade4/docker.env ps
openstack server image create --name snap-vm-daniel-ranya-atividade4 vm-daniel-ranya
openstack image show snap-vm-daniel-ranya-atividade4 -c id -c name -c status -c size -c disk_format -c min_disk
```

## O que aconteceu

A VM estava `ACTIVE`, com os três containers `Up (healthy)`, e o volume continuava montado. O snapshot foi criado às 02:10:30 UTC com ID `aa534820-acce-4597-969d-3740d3be4221`, formato `qcow2` e `min_disk` 20. O comando retorna com status `queued` e o Glance passa por `saving` antes de `active`; como o disco tem ~19 GB, a gravação levou cerca de 15 minutos — mais que a janela de espera da fase 28 (4 minutos) — e a fase de continuação `241-snapshot-check.sh` retomou a espera sem criar um segundo snapshot. Às 02:25:33 UTC a imagem estava `active`, com 7.980.580.864 bytes (7,4 GiB) em qcow2, tamanho virtual de 20 GiB, checksum `df11567104bf0f9f1c16849e345229a4` e visibilidade privada.

## Decisões

Criar o snapshot **depois** da verificação e do failover: o snapshot representa a VM já testada, não um estado intermediário. A imagem é privada e não é usada como base de novas VMs; ela existe como ponto de recuperação.

## Problemas

O status permaneceu `saving` por cerca de 15 minutos após a criação. Em vez de repetir o comando (o que criaria outra imagem), a fase 241 aguardou o mesmo snapshot terminar e registrou o estado final; ele chegou a `active` e foi confirmado por `openstack image show`.
