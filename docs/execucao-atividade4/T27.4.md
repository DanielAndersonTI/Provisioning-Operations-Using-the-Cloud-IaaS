## Objetivo

Mostrar a configuração que sustenta o acesso externo: cada listener da VIP aponta para um pool, o pool aponta para o membro `10.5.9.15` na porta publicada pelo container e para um monitor HTTP em `/health`. A fase 27 prova o comportamento; esta prova a configuração.

## Comandos

```bash
openstack loadbalancer listener show app-cpu-daniel-ranya \
  -c name -c protocol -c protocol_port -c default_pool_id -c operating_status
openstack loadbalancer pool show pool-app-cpu-daniel-ranya \
  -c name -c protocol -c lb_algorithm -c healthmonitor_id -c operating_status
openstack loadbalancer healthmonitor show <healthmonitor_id> \
  -c name -c type -c url_path -c delay -c timeout -c max_retries -c operating_status
openstack loadbalancer member list pool-app-cpu-daniel-ranya \
  -c name -c address -c protocol_port -c operating_status -c provisioning_status
```

## O que aconteceu

Os três listeners existentes desde a Atividade 3 continuam `ONLINE`, cada um com o seu pool padrão. Os pools continuam `ONLINE`, com `ROUND_ROBIN` e protocolo `HTTP`. Os monitores HTTP apontam para `/health`, com `delay` 5 s, `timeout` 4 s e `max_retries` 3 — exatamente o que a fase 27 viu reagir à queda do container.

## Decisões

Nenhum recurso do balanceador foi criado ou alterado nesta atividade: o caminho externo continua o mesmo da Atividade 3 e o que mudou foi apenas quem atende as portas `8000-8002` dentro da VM. O balanceador é compartilhado pela turma, então todos os comandos desta fase são de leitura.

## Problemas

Nenhum. A primeira tentativa usou nomes de listener supostos (`http-*`); a listagem mostrou os nomes reais (`app-cpu-daniel-ranya`, `app-memory-daniel-ranya`, `app-io-daniel-ranya`) e a fase foi corrigida antes da captura final.
