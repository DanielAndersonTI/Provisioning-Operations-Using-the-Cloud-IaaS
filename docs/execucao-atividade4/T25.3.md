# T25.3 — Publicação das imagens no Docker Hub

| Campo | Valor |
| --- | --- |

| Fase | Fase 25 |
| Status | concluída |
| Evidências | `T25.3-push`, `T25.3-report`, `T25.3-hub` |

## Objetivo

Publicar as tags `1.0.0` e `latest` das três imagens no Docker Hub e conferir pela API pública do Hub. O token nunca aparece em argumento de comando nem na evidência.

## Comandos

```bash
printf '%s' "$DOCKERHUB_TOKEN" | docker login -u "$DOCKERHUB_USER" --password-stdin
docker tag <usuario>/poi-<perfil>:1.0.0 <usuario>/poi-<perfil>:latest
docker push <usuario>/poi-<perfil>:1.0.0
docker push <usuario>/poi-<perfil>:latest
docker logout
```

## O que aconteceu

A primeira tentativa autenticou, mas o push foi recusado com `unauthorized: access token has insufficient scopes`: o token estava com escopo somente leitura. O token foi atualizado no Hub para **Read & Write** (mesmo valor) e a fase foi reexecutada. As três imagens foram publicadas com as tags `1.0.0` e `latest`, e a API do Hub confirmou as seis tags, com os tamanhos comprimidos entre 44.294.427 e 44.294.756 bytes.

## Decisões

O token entra por `--password-stdin`, nunca como argumento, e o script faz `docker logout` num `trap EXIT` — inclusive quando o push falha — para não deixar credencial em texto puro no `~/.docker/config.json` da VDI. A fase passou a falhar quando o push é recusado e quando o Hub não confirma as tags; antes ela seguia e terminava com exit 0, mascarando a falha.

## Problemas

Escopo do token (Read em vez de Read & Write), resolvido no Hub com a edição da permissão. Efeito colateral identificado e corrigido: a primeira execução mascarava a falha porque o `cap` do push não propagava o erro.
