# T14 — Snapshot final da VM e snapshot do volume de logs

**Data (UTC):** 2026-10-29T17:08–17:29Z
**Fase:** 14 — snapshots
**Status:** concluída
**Evidências:** `T14.1-*` a `T14.12-*` (ver tabela ao final), `RELATORIO.md` §4.9

## Objetivo

Fechar o estado final da entrega em dois artefatos: o snapshot da VM — que é o
pedido no enunciado — e o snapshot do volume de logs, que guarda a parte do
sistema que não entra no snapshot da VM.

## O que entrou em cada snapshot

O snapshot da VM (`openstack server image create`) copia o **disco raiz**: sistema
operacional, o código em `/opt/atividade3`, as unidades `systemd` com seus
drop-ins e o `/etc/fstab`. O volume de 1 GB é um disco separado, anexado à VM:
ele **não** entra nesse snapshot. Por isso cada um ganhou o seu.

## Comandos executados

```bash
# 1. volume: a API exige o volume em `available`
ssh ... 'sudo systemctl stop app-cpu app-memory app-io'
ssh ... 'sudo umount /mnt/atividade3-logs'
openstack server remove volume vm-daniel-ranya vol-daniel-ranya-logs
openstack volume snapshot create --volume vol-daniel-ranya-logs \
    --description 'Snapshot do volume de logs da Atividade 3' snap-vol-daniel-ranya-logs
openstack server add volume vm-daniel-ranya vol-daniel-ranya-logs
ssh ... 'sudo mount -a; sudo systemctl start app-cpu app-memory app-io'

# 2. VM: snapshot novo com nome temporário, conferência, troca do antigo
openstack server image create --name snap-vm-daniel-ranya-final vm-daniel-ranya
openstack image show snap-vm-daniel-ranya-final
openstack image delete snap-vm-daniel-ranya
openstack image set --name snap-vm-daniel-ranya snap-vm-daniel-ranya-final
```

## O que aconteceu

**O snapshot do volume pela API falhou com o volume anexado.**

```text
Invalid volume: Volume 2271182d-... status must be available,
but current status is: in-use. (HTTP 400)
```

O Cinder desta nuvem não aceita snapshot de volume em uso. A tentativa foi
repetida três vezes, sempre com a mesma resposta. A operação foi então
feita na ordem que ele permite, com as aplicações paradas:

```text
app-cpu / app-memory / app-io   stopped
/mnt/atividade3-logs            desmontado
vol-daniel-ranya-logs           available
snap-vol-daniel-ranya-logs      available (df5d86d9-f4d9-43d1-a805-7edf619355d0, 1 GB)
vol-daniel-ranya-logs           in-use de novo, /dev/vdb montado em /mnt/atividade3-logs
```

Os arquivos do volume estavam intactos na volta — três `app.log`, três `app.log.1`
rotacionados, `marca-antes-do-reboot.txt` e `teste.txt` —, e os três `app.log`
foram modificados **depois** do reanexo (17:25:33, 17:27:11 e 17:29:01); o do
memory termina com a mensagem de inicialização do processo. Isso mostra que os
serviços voltaram a escrever no volume, e não numa cópia local.

**O snapshot da VM foi refeito depois de todas as medições.** O snapshot antigo
(`7fb6d24c-…`, 1,85 GiB) era de antes das fases de medição; o novo inclui o código
final, os scripts de carga instalados e os drop-ins:

| Campo | Valor |
| --- | --- |
| Nome | `snap-vm-daniel-ranya` |
| ID | `6034d4a8-45bb-40ea-abe2-867e659e8f53` |
| Status | `active` |
| Formato | `qcow2` |
| Tamanho | 3.682.992.128 bytes ≈ 3,43 GiB |

A troca foi feita sem intervalo sem snapshot válido: o novo foi criado, conferido
como `active`, e só então o antigo foi apagado e o nome transferido com
`openstack image set --name`.

**Estado final conferido:**

```text
vm-daniel-ranya            ACTIVE   general.small (1 vCPU, 2 GB)
vol-daniel-ranya-logs      in-use   1 GB
snap-vol-daniel-ranya-logs available 1 GB
snap-vm-daniel-ranya       active   3,43 GiB
app-cpu / app-memory / app-io   active
porta 8100 / 8101 / 8102   HTTP 200 em /health e em /work (pela VIP)
```

## Decisões

- **Snapshot do volume desanexado, e não antes.** Esta nuvem recusa o snapshot com
  o volume em `in-use`; a alternativa de parar a VM inteira não traria vantagem,
  porque o volume é gravado pelas aplicações, e não pelo sistema.
- **Aplicações paradas durante o ciclo.** Sem escritor no ponto de montagem, o
  snapshot pega um sistema de arquivos consistente e o `umount` não fica
  pendurado em páginas sujas.
- **Snapshot da VM depois da volta ao `general.small`.** Um snapshot tirado em
  `general.medium` guardaria um flavor diferente do que o enunciado pede.
- **Nome final igual ao antigo.** Quem procurar pelo snapshot encontra
  `snap-vm-daniel-ranya`, como nas fases anteriores; o ID novo está no relatório.

## Problemas e pendências

- **Snapshot de volume com o volume anexado não é possível nesta nuvem** (erro
  HTTP 400). O ciclo desanexar → fotografar → reanexar resolve, mas exige parar
  as aplicações por alguns segundos.
- **Evidência de saúde capturada cedo demais.** Na primeira verificação depois do
  reanexo, `systemctl is-active` já era verdadeiro enquanto o socket ainda não
  escutava, e o balanceador ainda marcava o membro como fora — as portas
  locais responderam `HTTP 000` e a VIP `503`. A verificação passou a esperar a
  resposta 200 antes de registrar, e o resultado final é 200 em todas as portas.
  Esse comportamento é o esperado do health check do Octavia, que precisa de
  duas falhas/ok consecutivas para mudar o estado do membro.
- **Erro de expansão de variável em um dos comandos.** O primeiro comando de
  reinício usava `$(seq 1 30)` dentro de uma string entre aspas duplas e foi
  expandido no VDI, quebrando a sintaxe no host remoto; o comando foi corrigido
  com `\$(...)`.
