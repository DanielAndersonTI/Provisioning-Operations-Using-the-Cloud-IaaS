# T12.5 — Saturação: 8 e 16 clientes

**Data (UTC):** 2026-10-29T16:11–16:25Z
**Fase:** 12 — correções da revisão e medições complementares
**Status:** concluída
**Evidências:** `T12.5-sat-{cpu,memory,io}-c{8,16}`, `results/summary-saturation.csv`

> **Atualização (fase 19):** as células de 16 clientes dos perfis de memória e

## Objetivo

Levar a carga de um a oito e dezesseis clientes simultâneos, no tamanho padrão de
cada perfil, para descobrir onde a vazão para de crescer e o que acontece com a
latência e os erros nesse ponto.

## Comandos executados

```bash
for perfil in cpu memory io; do
  tamanho=$(case $perfil in cpu) echo 10;; memory) echo 32;; io) echo 1024;; esac)
  porta=$(case $perfil in cpu) echo 8100;; memory) echo 8101;; io) echo 8102;; esac)
  for conc in 8 16; do
    id="sat-$perfil-s$tamanho-c$conc"
    python3 scripts/load_test.py --url "http://150.165.85.77:$porta/work?size=$tamanho" \
        --level $conc --concurrency $conc --duration 30 --run-id $id ...
  done
done
```

Seis execuções de 30 s, com o mesmo protocolo das demais: aquecimento
descartado, monitor de 0,5 s na VM, contadores da aplicação antes e depois.

## O que aconteceu

```text
perfil   conc   vazão (req/s)   média (ms)   p95 (ms)   erros
cpu         4        19,83        201,7       274,2        0
cpu         8        21,52        370,8       396,1        0
cpu        16        21,78        731,4       785,6        0

memory      4        29,10        137,4       188,7        0
memory      8        33,21        240,3       277,0        0
memory     16        31,28        488,8      1334,7        0

io          4         6,57        609,6      1034,9        0
io          8         9,23        866,3      1119,4        0
io         16         9,65       1635,1      2052,5        0
```

O ponto de saturação aparece com clareza:

- **A vazão para de crescer.** De 4 para 16 clientes, a vazão do perfil de CPU
  vai de 19,8 para 21,8 req/s (+10 %), a de memória fica entre 29 e 33 req/s e a
  de IO entre 6,6 e 9,7 req/s. Quadruplicar os clientes não quadruplica a vazão.
- **A latência cresce junto.** Com a vazão constante, o acréscimo de clientes só
  enche fila: a média do perfil de CPU passa de 202 ms (4 clientes) para 731 ms
  (16 clientes) e o p95 do perfil de IO chega a 2,05 s.
- **Nenhuma requisição é recusada.** Os seis cenários terminaram com zero erros,
  e o contador de recusas da aplicação (`rejected_503`) ficou em zero em todos —
  o servidor nunca chegou a recusar trabalho por falta de vaga.

O número que explica o último item é a espera medida **dentro** da aplicação:
`mean_wait_ms` fica em 0,006 ms em todos os cenários, mesmo com 16 clientes. Ou
seja, quando a requisição chega ao servidor, uma vaga de trabalho está livre
imediatamente. A fila existe antes dele. Comparando com o trabalho médio do
perfil de memória nesse cenário — 50,1 ms —, o cliente observa 488,8 ms em média:
cerca de 440 ms são gastos no caminho VDI → balanceador → VM, não na aplicação.

## Decisões

- **Mesmo limite de clientes para os três perfis.** Uso 8 e 16 porque são os
  pontos em que a curva de vazão já dobrou o joelho em todos os perfis; não faz
  sentido alongar a matriz na VIP, onde a chegada é limitada antes da aplicação.
- **Vagas do servidor como hipótese, não como conclusão.** As vagas de trabalho
  (32 para CPU, 4 para memória, 16 para IO) e o comportamento quando elas enchem
  são medidos à parte, com a carga rodando dentro da VM (T12.8), porque pela VIP
  a recusa nunca é exercitada.

## Problemas e pendências

- **O limite observado é do caminho compartilhado, não da VM.** O balanceador
  `poi-atividades` é compartilhado com a turma, e a saída da VDI passa pela rede
  do host. Por isso os números absolutos desta matriz não devem ser lidos como
  capacidade da máquina — a comparação válida é entre cenários medidos na mesma
  sessão, como em T12.4 e T12.6.
