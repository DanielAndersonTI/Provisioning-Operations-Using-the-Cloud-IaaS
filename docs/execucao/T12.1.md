# T12.1 — Redeploy das aplicações com contadores internos

**Data (UTC):** 2026-10-29T15:50:09Z
**Fase:** 12 — correções da revisão e medições complementares
**Status:** concluída
**Evidências:** `T12.1-upload-apps` · `T12.1-checksum` · `T12.1-restart` · `T12.1-metrics-vip`

## Objetivo

Publicar na VM a versão das aplicações que expõe `GET /metrics`, sem mudar nada
do comportamento HTTP que já estava validado (`/health` e `/work`). As
medições da fase 10 enxergavam apenas o lado do cliente; os contadores internos
acrescentam o outro lado: quanto tempo cada requisição esperou por uma vaga de
trabalho, quanto durou o trabalho em si e quantas foram recusadas por falta de
vaga.

## Comandos executados

```bash
tar czf - -C ~/atividade3 apps | ssh ... 'sudo tar xzf - -C /opt/atividade3'
sha256sum ~/atividade3/apps/server.py
ssh ... 'sha256sum /opt/atividade3/apps/server.py'
ssh ... 'sudo systemctl restart app-cpu app-memory app-io; systemctl is-active ...'
curl -s http://150.165.85.77:8100/metrics   # e 8101, 8102
```

## O que aconteceu

O código foi enviado pelo mesmo caminho das outras fases — `tar` pelo túnel SSH
do balanceador, já que a VM não tem IP público — e os três serviços foram
reiniciados para carregar o módulo novo. A conferência de integridade mostra o
mesmo hash nos dois lados:

```text
80ac1f492332eae2773df48da16e778617b4f9c1546370123def5c40ce3821d8  /home/osboxes/atividade3/apps/server.py
80ac1f492332eae2773df48da16e778617b4f9c1546370123def5c40ce3821d8  /opt/atividade3/apps/server.py
```

Os três serviços voltaram `active` e o endpoint novo respondeu pela VIP, nas
três portas, com os contadores zerados porque o processo acabou de subir:

```json
{"profile": "cpu", "max_concurrency": 32, "uptime_seconds": 2.663,
 "requests": 0, "ok": 0, "rejected_503": 0, "failed": 0, "completed": 0,
 "inflight": 0, "max_inflight": 0, "wait_seconds_total": 0.0,
 "work_seconds_total": 0.0, "mean_wait_ms": 0.0, "mean_work_ms": 0.0,
 "max_work_ms": 0.0}
```

## Decisões

- **Contadores cumulativos, lidos antes e depois de cada execução.** Reiniciar o
  serviço entre cenários zeraria o estado e esconderia a fila que sobra de um
  cenário para o seguinte; subtrair duas leituras dá o intervalo exato sem
  tocar no processo.
- **`/metrics` não conta como requisição de trabalho.** A leitura pela VIP não
  altera `requests`, então medir não perturba o que está sendo medido.
- **Recusa é registrada no ponto em que acontece.** O `503` é contado antes de
  qualquer trabalho, para que a soma `ok + recusadas + falhas` feche com o que o
  cliente viu.

## Problemas e pendências

- Nenhum. O hash e a resposta dos três perfis confirmam o deploy.
