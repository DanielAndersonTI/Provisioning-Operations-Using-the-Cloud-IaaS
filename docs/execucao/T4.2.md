# T4.2 — Acesso SSH pela VIP

**Data (UTC):** 2026-10-29T03:12:52Z
**Fase:** 4 — acesso SSH pelo balanceador
**Status:** concluída
**Evidências:** `evidencias/T4.2-ssh-vip.txt` · `evidencias/T4.2-ssh-vip.png`

## Objetivo

Provar que a VM é alcançável de fora — da VDI, sem IP público na VM — usando
apenas `150.165.85.77:2222`. Esta é a validação do requisito do enunciado
"configurar o balanceador `poi-atividades` para acesso SSH".

## Comandos executados

```bash
ssh -i ~/.ssh/atividade3-daniel-ranya -p 2222 \
    -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null \
    -o ConnectTimeout=15 -o BatchMode=yes \
    ubuntu@150.165.85.77 'hostname; uname -a; head -2 /etc/os-release'
```

## O que aconteceu

A conexão foi aceita na primeira tentativa. O host remoto respondeu
`vm-daniel-ranya`, kernel `6.8.0-87-generic` e `Ubuntu 24.04.3 LTS` — ou seja, o
tráfego saiu da VDI, entrou no amphora na porta 2222, foi encaminhado para
`10.5.9.15:22` e chegou à VM.

Dois detalhes que valem registrar:

- `BatchMode=yes` garante que a autenticação é por chave e nunca por senha. Se a
  chave não valesse, o comando falharia em vez de pedir senha e travar.
- `StrictHostKeyChecking=no` e `UserKnownHostsFile=/dev/null` são apropriados
  aqui porque a VM é efêmera e recriada a cada execução; manter chaves de host
  antigas só geraria aviso de "host key changed".

A partir desta task, o canal SSH pela VIP passou a ser a via de administração da
VM — todas as fases seguintes (deploy, volume, logs) usam exatamente este canal.

## Decisões

- Usar o SSH pela VIP como único canal de administração da VM: não há IP
  flutuante e não há motivo para criar um.
- Fixar `-p 2222` em todas as fases seguintes por meio de uma variável comum.
