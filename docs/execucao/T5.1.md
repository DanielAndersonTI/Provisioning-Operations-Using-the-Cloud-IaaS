## Objetivo

Conhecer a VM que acabou de subir (o que já veio instalado, quanto de CPU e
memória existe, quanto espaço livre sobrou) e criar o usuário e os diretórios
que a aplicação vai usar.

## Comandos executados

```bash
ssh ... ubuntu@150.165.85.77 'cloud-init status; hostnamectl; python3 -V; nproc; free -m; df -h /'
ssh ... ubuntu@150.165.85.77 'sudo useradd --system --no-create-home --shell /usr/sbin/nologin appsvc
    sudo install -d -o root -g root -m 0755 /opt/atividade3 /opt/atividade3/apps
    sudo install -d -o appsvc -g appsvc -m 0750 /var/log/atividade3{,/cpu,/memory,/io}'
```

## O que aconteceu

O `cloud-init` já havia terminado (`status: done`), então a VM está pronta para
receber trabalho e nada do que eu fizer vai colidir com uma inicialização em
andamento.

O inventário da máquina:

| Item | Valor | Por que importa |
| --- | --- | --- |
| hostname | `vm-daniel-ranya` | nome coerente com o restante do grupo |
| kernel | `6.8.0-87-generic` | |
| Python | 3.12.3 | já presente; não foi preciso instalar nada |
| vCPU | 1 | é o `general.small` |
| memória | 1968 MB | |
| disco raiz | 19 GB, 1,7 GB usados (9%) | sobra espaço, mas o volume separado é exigência |

Como a aplicação é um servidor HTTP simples da biblioteca padrão do Python, não
há dependência para instalar: `python3` já vem na imagem.

Criei um usuário de sistema `appsvc` (`uid 999`, shell `/usr/sbin/nologin`) para
que os serviços **não** rodem como `ubuntu`. O prompt de login fica desativado,
então mesmo que a senha do serviço vazasse não haveria como entrar.

Os diretórios seguem o padrão do `systemd`:

| Caminho | Dono | Permissão | Uso |
| --- | --- | --- | --- |
| `/opt/atividade3` | root | 0755 | raiz do deploy |
| `/opt/atividade3/apps` | ubuntu | 0775 | código, extraído pelo `tar` que rodou via `sudo` |
| `/var/log/atividade3` | appsvc | 0750 | logs antes da mudança para o volume (fase 7) |
| `/var/log/atividade3/{cpu,memory,io}` | appsvc | 0750 | um por perfil |

O `apps/` ficou como `ubuntu:ubuntu 0775` porque o `tar` da T5.2 roda como root
mas preserva o dono dos arquivos do pacote. Não é problema: o serviço só precisa
**ler** (`o+r` está presente) e não escreve no próprio código.

## Decisões

- Usuário de sistema sem shell e sem home, em vez de rodar como `ubuntu`.
- Código em `/opt` (somente leitura) e logs em `/var/log` com dono próprio: o
  serviço não precisa escrever no próprio binário.

## Problemas e pendências

A primeira captura do `ls -ld` terminou com código 2: o diretório
`/var/log/atividade3` é `0750 appsvc` e o usuário `ubuntu` não consegue listar os
subdiretórios dentro dele. É exatamente o comportamento desejado — a captura foi
refeita com `sudo` para mostrar os quatro diretórios.
