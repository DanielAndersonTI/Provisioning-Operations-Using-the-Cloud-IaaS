# T5.4 — Habilitação e início dos serviços

**Data (UTC):** 2026-10-29T03:16:02Z
**Fase:** 5 — deploy das aplicações
**Status:** concluída
**Evidências:** `evidencias/T5.4-enable-start.txt` · `T5.4-enable-start.png`

## Objetivo

Colocar os três serviços para rodar agora e também em todo boot futuro.

## Comandos executados

```bash
ssh ... ubuntu@150.165.85.77 'sudo systemctl daemon-reload
    sudo systemctl enable --now app-cpu app-memory app-io
    sleep 3
    systemctl is-enabled app-cpu app-memory app-io
    systemctl is-active app-cpu app-memory app-io'
```

## O que aconteceu

O `daemon-reload` fez o `systemd` reler as units recém-copiadas. O
`enable --now` faz as duas coisas de uma vez: cria o link em
`multi-user.target.wants` (para subir no boot) e já inicia o serviço.

A saída mostra seis linhas:

```text
enabled
enabled
enabled
active
active
active
```

`enabled` responde "vai subir no boot?" e `active` responde "está rodando
agora?". As duas respostas importam: um serviço `active` mas `disabled` some no
próximo reboot, e é justamente o reboot do T6.4 que prova o contrário.

O `sleep 3` antes do `is-active` dá tempo de o Python abrir o socket; sem ele o
`systemd` poderia reportar `activating` no instante seguinte ao `start`.


## Decisões

- `enable --now`, em vez de `enable` e depois `start`: um comando, um estado.
- Verificar `is-enabled` **e** `is-active`, não só um dos dois.
