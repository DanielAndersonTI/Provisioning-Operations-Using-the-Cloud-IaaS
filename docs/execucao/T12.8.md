# T12.8 — Carga local dentro da VM: o limite do próprio servidor

**Data (UTC):** 2026-10-29T16:43–16:45Z
**Fase:** 16 — carga local e comportamento de admissão
**Status:** concluída
**Evidências:** `T12.8-local-setup`, `T12.8-local-{cpu,memory,io}-c{8,32}`, `results/measurements-local.csv`, `results/app-metrics-local.csv`

## Objetivo

Medir o que acontece quando a demanda chega ao servidor mais rápido do que ele
consegue atender — inclusive a recusa explícita (HTTP 503) —, sem o balanceador
compartilhado limitando a chegada antes da aplicação.

## Por que a carga roda dentro da VM

Nas matrizes pela VIP (T12.4, T12.5) não houve uma única recusa, e a espera
medida dentro da aplicação ficou em 0,006 ms mesmo com 16 clientes: a fila está
no caminho, não no servidor. Para exercitar as vagas de trabalho e o caminho de
recusa, o gerador de carga desta fase é executado **na própria VM**, apontando
para `127.0.0.1`.

## Comandos executados

```bash
scp scripts/load_test.py ubuntu@150.165.85.77:/tmp/ >/dev/null   # via ssh + tee
ssh ... 'sudo install -m 0755 /tmp/load_test.py /opt/atividade3/scripts/load_test.py'

for perfil in cpu memory io; do
  porta=$(case $perfil in cpu) echo 8000;; memory) echo 8001;; io) echo 8002;; esac)
  tamanho=$(case $perfil in cpu) echo 10;; memory) echo 32;; io) echo 1024;; esac)
  for conc in 8 32; do
    curl -s "http://127.0.0.1:$porta/metrics" > /tmp/before.json
    ssh ... "python3 /opt/atividade3/scripts/load_test.py \
             --url 'http://127.0.0.1:$porta/work?size=$tamanho' \
             --concurrency $conc --duration 20 --run-id local-$perfil-c$conc ..."
    curl -s "http://127.0.0.1:$porta/metrics" > /tmp/after.json
  done
done
```

Seis execuções de 20 s. As vagas de trabalho de cada servidor são 32 (CPU), 4
(memória) e 16 (IO); 32 clientes passam do limite dos perfis de memória e IO.

## O que aconteceu

```text
execução          req/s   sucesso   erro    503   média (ms)   trabalho (ms)
local-cpu-c8      20,92      424      0      0      381,3           365,7
local-cpu-c32     20,05      417      0      0     1567,6          1346,1
local-memory-c8   31,99      658      0      0      244,9            48,1
local-memory-c32  21,46      638      0      0     1069,3            49,6
local-io-c8        4,09       82      0      0     1956,0          1907,8
local-io-c32     587,79      127  13117  13117       52,1            23,8
```

Três comportamentos distintos, todos previstos pelo limite de vagas de cada
servidor:

- **CPU — o limite é o vCPU, não a admissão.** Com 32 clientes as 32 vagas foram
  ocupadas (pico de requisições em voo igual a 32), sem nenhuma recusa, porque o
  limite coincide com o número de clientes. O que muda é o tempo de trabalho:
  365 ms com 8 clientes e 1346 ms com 32, para a mesma vazão de ~20 req/s — os
  threads se revezam em um único vCPU.
- **Memória — o trabalho é curto demais para encher as vagas.** A carga de
  memória leva ~50 ms; com cliente e servidor dividindo o mesmo vCPU, as
  requisições não se sobrepõem o suficiente para ocupar as quatro vagas, e não
  há recusa. O que cresce é a espera do cliente: 1,07 s de média e p95 de 4,0 s
  com 32 clientes — fila no núcleo e nos sockets, não nas vagas.
- **IO — a recusa aparece.** Cada escrita fica bloqueada por cerca de dois
  segundos, o que libera o GIL e permite que 16 threads trabalhem de fato em
  paralelo. A 17ª requisição simultânea em diante é recusada na hora: em 20 s,
  13 117 das 13 244 tentativas (99,04 %) receberam 503, com mediana de 7,2 ms —
  a recusa é rápida, e não uma espera longa. A vazão de sucesso ficou em
  5,6 req/s.

O contador `rejected_503` do `/metrics` acompanhou exatamente as recusas vistas
pelo cliente (13 117 nos dois lados), o que valida a instrumentação usada nas
demais fases.

## Decisões

- **Falhar rápido em vez de enfileirar sem limite.** O servidor recusa quando
  todas as vagas estão ocupadas; isso mantém a memória e o tempo de resposta sob
  controle e devolve ao cliente um sinal claro (503) em vez de um timeout.
- **Ressalva declarada: cliente e servidor na mesma VM.** Os números absolutos
  desta fase não são comparáveis aos da VIP — o gerador de carga disputa o mesmo
  vCPU com o servidor e infla o tempo de trabalho. O que se mede aqui é o
  comportamento de admissão: vagas ocupadas, recusas e espera.

## Problemas e pendências

- **Nenhuma recusa nos perfis de CPU e memória.** Não é uma falha do experimento:
  é o resultado de o trabalho ser curto e de o cliente consumir o mesmo vCPU. A
  demonstração do caminho de recusa fica com o perfil de IO, onde há bloqueio de
  E/S e as threads realmente se sobrepõem.
- **`max_inflight` é cumulativo desde o restart dos serviços.** O valor reportado
  é o pico desde que o processo subiu; por isso o cenário de 8 clientes mostra o
  pico de uma execução anterior quando ela foi maior. A leitura correta é "o pico
  já chegou a este valor", não "nesta janela houve este pico".
