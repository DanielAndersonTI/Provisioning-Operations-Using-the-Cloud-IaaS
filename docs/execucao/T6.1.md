# T6.1 — Criação e anexação do volume

**Data (UTC):** 2026-10-29T03:27:31Z
**Fase:** 6 — volume de 1 GB para logs
**Status:** concluída
**Evidências:** `evidencias/T6.1-volume-create.txt` · `T6.1-volume-create.png` · `T6.1-volume-attach.*` · `T6.1-volume-show.*` · `T6.1-volume-list.*`

## Objetivo

Criar um volume de 1 GB no Cinder e anexá-lo à VM, para que os logs das
aplicações não fiquem no disco raiz — é o requisito "volume de 1 GB anexado,
montado e utilizado para os logs".

## Comandos executados

```bash
openstack volume create --size 1 --description 'Logs das aplicacoes - Atividade 3' vol-daniel-ranya-logs
# aguarda o volume sair de `creating` (ver "Problemas")
openstack server add volume vm-daniel-ranya vol-daniel-ranya-logs
openstack volume show vol-daniel-ranya-logs -c id -c name -c size -c status -c attachments
openstack volume list
```

## O que aconteceu

O volume `vol-daniel-ranya-logs` (`2271182d-ac0c-4dd9-bcf7-cc535379f532`) foi
criado com 1 GB, tipo `__DEFAULT__`, na zona `nova`. Como a criação é
assíncrona, o script consulta o status em laço até chegar a `available` antes de
anexar — anexar em `creating` é recusado pela API.

A anexação devolveu o device atribuído pelo hipervisor:

| Campo | Valor |
| --- | --- |
| Volume | `2271182d-ac0c-4dd9-bcf7-cc535379f532` |
| Server | `bdc0447e-fb71-48c8-9ce2-04a8c5e20ee0` |
| Device | `/dev/vdb` |
| Delete on termination | `False` |

`Delete on termination=False` é o padrão e foi mantido de propósito: apagar a VM
não deve apagar o volume junto.

Depois da anexação o volume fica `in-use` e o campo `attachments` traz
`device: /dev/vdb` e `attached_at`. O script **lê o device da API** em vez de
supor `vdb` — se a VM já tivesse outro volume, o próximo device seria `vdc`.

## Decisões

- 1 GB, o tamanho mínimo e o que o enunciado pede; log de aplicação é texto e
  gira, não precisa de mais.
- Nome com o sufixo do grupo, porque o projeto é compartilhado com a turma.
- Ler o device pela API em vez de fixar `/dev/vdb` no script.

## Problemas e pendências

A primeira execução usou `--wait` em `openstack volume create` e em
`openstack server add volume`; o cliente instalado (5.8.0) não aceita essa flag
nesses dois comandos (`unrecognized arguments: --wait`). O efeito colateral foi
pior do que o erro: o script seguiu adiante sem volume nenhum, o filtro do
`lsblk` devolveu vazio e o comando seguinte tentou formatar um device
inexistente. A correção foi trocar `--wait` por um laço de consulta
(`wait_volume_status`) e repetir a fase do começo.
