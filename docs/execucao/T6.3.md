# T6.3 — Montagem persistente no `/etc/fstab`

**Data (UTC):** 2026-10-29T03:28:57Z
**Fase:** 6 — volume de 1 GB para logs
**Status:** concluída
**Evidências:** `evidencias/T6.3-fstab-write.txt` · `T6.3-fstab-write.png` · `T6.3-remount-check.*`

## Objetivo

Fazer o volume ser montado sozinho no boot, por UUID, sem risco de a VM não
subir caso o volume não esteja disponível.

## Comandos executados

```bash
ssh ... 'UUID=$(sudo blkid -s UUID -o value /dev/vdb); sudo cp /etc/fstab /etc/fstab.bak
    { echo "LABEL=cloudimg-rootfs / ext4 discard,commit=30,errors=remount-ro 0 1"; \
      echo "LABEL=BOOT /boot ext4 defaults 0 2"; \
      echo "LABEL=UEFI /boot/efi vfat umask=0077 0 1"; \
      echo "# volume de logs da Atividade 3 (montado por UUID)"; \
      echo "UUID=$UUID /mnt/atividade3-logs ext4 defaults,nofail 0 2"; } | sudo tee /etc/fstab'
ssh ... 'sudo umount /mnt/atividade3-logs; sudo mount -a; findmnt /mnt/atividade3-logs
    sudo cat /mnt/atividade3-logs/teste.txt
    systemctl list-units --type=mount --all | grep -i atividade'
```

## O que aconteceu

O `/etc/fstab` final ficou com quatro linhas — as três da imagem mais o volume:

```text
LABEL=cloudimg-rootfs / ext4 discard,commit=30,errors=remount-ro 0 1
LABEL=BOOT /boot ext4 defaults 0 2
LABEL=UEFI /boot/efi vfat umask=0077 0 1
# volume de logs da Atividade 3 (montado por UUID)
UUID=1de1bd6e-b421-49ca-abeb-976698e2abd1 /mnt/atividade3-logs ext4 defaults,nofail 0 2
```

Três detalhes:

- **UUID e não `/dev/vdb`**: a ordem dos discos pode mudar entre boots; o UUID
  não.
- **`nofail`**: se o volume não existir no boot (por exemplo, num snapshot
  restaurado sem o volume anexado), o boot segue em vez de cair em modo de
  emergência. É a diferença entre "sem logs" e "VM inacessível".
- **Cópia em `/etc/fstab.bak`** antes de escrever: o arquivo inteiro foi
  reescrito, e um `/etc/fstab` quebrado deixa a VM sem console.

O teste de persistência **sem reboot** foi feito desmontando e usando
`mount -a`, que lê o `fstab` e monta o que estiver faltando. O arquivo
`teste.txt` escrito na T6.2 continuou legível depois da remontagem — os dados
estão no volume, não em uma montagem temporária.

O `systemd` passou a enxergar o ponto de montagem como unit própria
(`mnt-atividade3\x2dlogs.mount`), o que é o que garante o ordenamento com os
serviços da fase 7.

## Saída

```text
TARGET               SOURCE   FSTYPE OPTIONS
/mnt/atividade3-logs /dev/vdb ext4   rw,relatime

volume-ok

  mnt-atividade3\x2dlogs.mount  loaded  active  mounted /mnt/atividade3-logs
```

## Decisões

- UUID em vez de rótulo em `/etc/fstab`, e `nofail` obrigatório.
- Reescrever o arquivo inteiro a partir das três linhas conhecidas: o
  `/etc/fstab` anterior já havia sido corrompido por uma execução anterior (ver
  T6.1), e acrescentar linha a linha perpetuaria o problema.

## Problemas e pendências

A execução anterior (a que falhou por causa do `--wait`) deixou três linhas
`UUID=...` soltas no `/etc/fstab`, geradas por um `blkid` chamado sem argumento
— que lista **todos** os dispositivos. A reescrita completa descrita acima
removeu as três.
