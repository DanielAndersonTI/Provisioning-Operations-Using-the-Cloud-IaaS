# T13 — Demanda × provisionamento: a mesma VM em `general.medium`

**Data (UTC):** 2026-10-29T16:47–17:05Z
**Fase:** 13 — resize para cima, medição e volta
**Status:** concluída
**Evidências:** `T13.1-flavor-before`, `T13.1-vm-before`, `T13.2-resize-request`, `T13.2-resize-status`, `T13.3-resize-confirm`, `T13.4-medium-resources`, `T13.5-med-{cpu,memory,io}-c{1,2,4,8}`, `T13.6-resize-back`, `T13.6-resize-back-status`, `T13.7-resize-back-confirm`, `T13.8-small-again`, `T13.8-flavor-final`, `T13.9-summary`, `results/summary-medium.csv`

## Objetivo

Mostrar que a oferta de recursos muda o resultado da mesma carga: redimensionar
a mesma VM de `general.small` (1 vCPU, 2 GB) para `general.medium` (2 vCPU,
4 GB), repetir uma matriz curta e voltar ao flavor pedido no enunciado.

## Por que pela mesma VM

Recriar uma segunda VM introduziria diferenças de rede, de IP e de posição no
hipervisor junto com a diferença de flavor. Redimensionar mantém disco, IP,
nome, serviços e volume; a única variável é o provisionamento.

## Comandos executados

```bash
openstack server show vm-daniel-ranya -f value -c name -c status -c flavor
openstack server resize --flavor general.medium vm-daniel-ranya
# ... espera sair de RESIZE
openstack server resize confirm vm-daniel-ranya
# ... espera ACTIVE e SSH responder
# 12 execuções de 30 s (3 perfis × 1, 2, 4 e 8 clientes)
openstack server resize --flavor general.small vm-daniel-ranya
openstack server resize confirm vm-daniel-ranya
```

## O que aconteceu

**Antes.** A VM estava `ACTIVE`, `general.small (7441c7d9-…, 1 vCPU, 2048 MB)`.

**O resize.** O pedido foi aceito em 16:47:31 e a VM entrou em `RESIZE`; cerca de
três minutos e meio depois estava em `VERIFY_RESIZE` com o novo flavor
`general.medium (69495bdc-…, 2 vCPU, 4096 MB)`. A confirmação foi dada às
16:51:25 e a VM voltou a `ACTIVE`.

**O que sobreviveu ao reboot.** O resize reinicia a VM; a conferência logo depois
mostra que nada precisou ser refeito:

**A carga nos dois provisionamentos.** Mesma carga, mesmo tamanho de trabalho,

(valores em requisições por segundo de sucesso)

**Leitura dos números.**

- **Com um cliente não há ganho nenhum** — 8,58 contra 8,53 no perfil de CPU. O
  trabalho de uma requisição é sequencial; um segundo núcleo não acelera uma
  única thread. É a demonstração de que o gargalo, com um cliente, é o trabalho
  em si, não o provisionamento.
- **De dois clientes em diante o flavor maior se paga.** No perfil de CPU a
  vazão dobra com quatro clientes (19,83 → 37,65 rps) e o tempo de trabalho por
  requisição cai de 97 ms para 59 ms: na VM pequena os clientes se revezavam no
  único núcleo.
- **A memória ganha menos e satura antes.** O medium com dois clientes (25,3 rps)
  praticamente alcança o small com quatro (29,1 rps); a partir daí os dois
  empatam, porque o limite passa a ser a alocação e a liberação dos 32 MiB por
  requisição, não o número de núcleos.
- **O IO é o mais beneficiado (2,3×).** Com dois vCPU, mais threads conseguem
  ficar bloqueadas na escrita ao mesmo tempo e a preparação dos dados deixa de
  competir com o núcleo único.
- **O medium também satura.** Com oito clientes o perfil de CPU cai para 34,4 rps
  e o trabalho por requisição dobra para 100 ms; o p95 vai a 1.115 ms. O teto
  com dois vCPU fica na faixa de 35 a 38 rps para este perfil.

**A volta.** Depois das medições a VM foi redimensionada de volta: `RESIZE` →
`VERIFY_RESIZE` → confirmação → `ACTIVE`, com a conferência final em
17:04:53 mostrando `general.small (7441c7d9-…)`, `nproc` = 1, 1967 MiB, os três
serviços `active`, o volume montado e as três portas respondendo 200. A VM ficou
no provisionamento pedido no enunciado.

## Decisões

- **Oito clientes no flavor maior, quatro no pequeno.** A matriz do pequeno já
  estava fechada nos cenários base; a do medium vai até oito porque é a partir
  daí que o novo teto aparece (vazão cai e o trabalho dobra).
- **Voltar para `general.small` ao final.** O enunciado pede uma VM nesse flavor;
  deixar o experimento no flavor maior mudaria o entregável. O snapshot final é
  tirado depois da volta (T14).
- **Espera do SSH e das unidades depois do resize.** O reboot é rápido, mas o
  health check do balanceador e as unidades `systemd` levam alguns segundos; o
  script espera antes de medir, para não registrar erros que não são da carga.

## Problemas e pendências

- **`RESIZE` durou mais que o previsto.** Foram cerca de 40 verificações de
  status (≈ 3,5 min) até `VERIFY_RESIZE`; o limite do laço é de 80 verificações,
  então houve folga. Se o nó estiver ocupado, o mesmo resize pode demorar mais.
- **O `max_inflight` dos contadores é acumulado desde o restart.** Ele zera no
  reboot do resize e volta a acumular; por isso não deve ser lido como pico por
  execução.
