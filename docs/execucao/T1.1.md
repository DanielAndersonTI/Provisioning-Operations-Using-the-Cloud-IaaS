## Objetivo

Levantar o que a nuvem oferece e o que já existe no projeto: flavors, imagens,
servidores e snapshots são as quatro listagens pedidas explicitamente no roteiro
da atividade. Sem isso eu não saberia quais nomes usar em `server create` nem se
o nome da minha VM já estava ocupado por outro grupo.

## Comandos executados

```bash
openstack flavor list
openstack image list
openstack server list
openstack image list --property image_type=snapshot
```

## O que aconteceu

**Flavors.** O projeto expõe cinco tamanhos, todos públicos e com prefixo
`general.`: `general.small` (1 vCPU, 2 GB, 20 GB de disco), `general.medium`
(2 vCPU, 4 GB), `general.large` (4 vCPU, 8 GB), `general.xlarge` (8 vCPU, 16 GB)
e `general.xlarge.okd` (8 vCPU, 16 GB, 100 GB). O enunciado pede
`general.small`, que é o menor deles — importante porque os experimentos medem
justamente o efeito de uma máquina pequena.

**Imagens.** A imagem de sistema pedida é `ubuntu-24.04`, além de `ubuntu-20.04`,
`rocky-10` e imagens de deploy do próprio Octavia (`deploy-initrd`,
`deploy-vmlinuz`). Também aparecem imagens de outros grupos, o que confirma que
o projeto da disciplina é compartilhado.

**Servidores.** Já existiam várias VMs de outros grupos e três máquinas de um
cluster Kubernetes (`control-plane`, `worker-1`, `worker-2`), todas na rede
`provider`, com endereços privados. Nenhuma tem IP flutuante — o que explica por
que o acesso externo precisa passar pelo balanceador.

**Snapshots.** Havia onze imagens do tipo snapshot, de outros grupos. Isso
mostra que o snapshot da minha VM precisa de um nome próprio para não se
confundir com os demais.

- Usar exatamente `general.small` e `ubuntu-24.04`, como o enunciado exige.
- Nomear todos os recursos com o sufixo `daniel-ranya` para não colidir com os
  dos outros grupos, que compartilham o mesmo projeto.
