# T8.3 — Teste externo pela VIP

**Data (UTC):** 2026-10-29T04:16:38Z
**Fase:** 8 — aplicações pelo balanceador
**Status:** concluída
**Evidências:** `evidencias/T8.3-health-vip.txt` · `T8.3-health-vip.png` · `T8.3-work-vip.*` · `T8.3-smoke-vip.*`

## Objetivo

Provar que as três aplicações respondem a partir da VDI, pelo endereço público do
balanceador — que é exatamente o caminho que qualquer cliente de fora usa.

## Comandos executados

```bash
for p in 8100:CPU 8101:MEMORY 8102:IO; do
    curl -sS -m 10 -w ' HTTP %{http_code} em %{time_total}s\n' http://150.165.85.77:$port/health
done
curl -sS -m 60 "http://150.165.85.77:8100/work?size=10"
curl -sS -m 60 "http://150.165.85.77:8101/work?size=32"
curl -sS -m 60 "http://150.165.85.77:8102/work?size=1024"
ssh ... ubuntu@150.165.85.77 'A3_HOST=150.165.85.77 A3_CPU_PORT=8100 \
    A3_MEMORY_PORT=8101 A3_IO_PORT=8102 a3-smoke'
```

## O que aconteceu

Os três `/health` responderam `200` pela VIP, e cada um identificou o perfil
certo — ou seja, não há membro trocado entre pools:

```text
CPU     8100 {"status": "ok", "profile": "cpu"}    HTTP 200 em 0.057s
MEMORY  8101 {"status": "ok", "profile": "memory"} HTTP 200 em 0.046s
IO      8102 {"status": "ok", "profile": "io"}     HTTP 200 em 0.046s
```

Os `/work` também responderam `200` com o resultado do trabalho:

| Porta | Pedido | Tempo de parede | Resposta |
| --- | --- | --- | --- |
| 8100 | `/work?size=10` | 0,100 s | `sha256` + `iterations: 10` |
| 8101 | `/work?size=32` | 0,399 s | `allocated_mib: 32` + checksum |
| 8102 | `/work?size=1024` | 0,169 s | 1 MiB lido e escrito |

O `a3-smoke` rodou **de dentro da VM** apontando para a VIP (`A3_HOST=150.165.85.77`),
o que prova o caminho completo: a requisição sai da VM, entra no amphora pelo
endereço público e volta para a própria VM. É um teste mais rigoroso do que o
`curl` da VDI, porque exercita também a regra do grupo de segurança aplicada ao
tráfego que chega do amphora.

Comparando com a T5.5 (mesmas aplicações em `127.0.0.1`), a latência subiu de
~0,02–0,05 s para ~0,05–0,07 s no `/health`: esse acréscimo é o salto extra pela
VIP, não uma degradação do serviço.

```text
memory   8101   200     200      0.035152        32  {"profile": "memory", ...}
io       8102   200     200      0.013774      1024  {"profile": "io", ...}
```

## Decisões

- Testar a partir da VDI (cliente externo) **e** de dentro da VM (caminho
  completo pelo amphora).
- Usar os mesmos tamanhos de trabalho do `a3-smoke` da fase 5, para as duas
  medições serem comparáveis.

## Problemas e pendências

A primeira tentativa de `T8.3-smoke-vip` executou `a3-smoke` diretamente na VDI e
falhou com `command not found`: o script está instalado na VM, não na VDI. O
comando passou a ser executado por SSH na VM.
