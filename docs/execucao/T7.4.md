# T7.4 — Rotação de logs

**Data (UTC):** 2026-10-29T03:50:36Z
**Fase:** 7 — logs no volume e rotação
**Status:** concluída
**Evidências:** `evidencias/T7.4-logrotate-install.txt` · `T7.4-logrotate-install.png` · `T7.4-logrotate-force.*` · `T7.4-logrotate-debug.*` · `T7.4-logrotate-timer.*`

## Objetivo

Evitar que os logs cresçam sem limite dentro de um volume de 1 GB. Um volume
que enche derruba a aplicação — então a rotação não é enfeite, é parte do
requisito "usar o volume para logs".

## Comandos executados

```bash
cat payload/logs/logrotate/atividade3 | ssh ... 'sudo tee /etc/logrotate.d/atividade3 >/dev/null
    sudo chmod 0644 /etc/logrotate.d/atividade3'
ssh ... 'sudo logrotate -f -v /etc/logrotate.d/atividade3'
ssh ... 'systemctl list-timers logrotate.timer --no-pager; systemctl is-enabled logrotate.timer'
```

## O que aconteceu

A configuração instalada:

```text
/mnt/atividade3-logs/*/app.log {
    daily
    rotate 7
    maxsize 10M
    compress
    delaycompress
    missingok
    notifempty
    copytruncate
}
```

| Diretiva | Efeito |
| --- | --- |
| `daily` + `rotate 7` | guarda uma semana de histórico |
| `maxsize 10M` | roda também quando o arquivo passa de 10 MB, sem esperar o dia |
| `compress` + `delaycompress` | o arquivo recém-rotacionado fica legível; os anteriores vão para `.gz` |
| `missingok` / `notifempty` | não reclama de perfil sem log e não rotaciona arquivo vazio |
| `copytruncate` | **essencial aqui**: o `systemd` mantém o arquivo aberto; copiar e truncar evita ter de reiniciar o serviço a cada rotação |

O teste com `-f -v` forçou uma rotação imediata e mostrou a sequência completa
para cada perfil: renomear os `.gz` antigos, copiar `app.log` para `app.log.1`
e truncar `app.log`. O resultado no volume:

```text
/mnt/atividade3-logs/cpu:
-rw-r--r-- 1 root root   0 Oct 29 03:50 app.log
-rw-r--r-- 1 root root 140 Oct 29 03:50 app.log.1
```

O `app.log` voltou a 0 byte e o conteúdo anterior está no `.1` — exatamente o
comportamento esperado de `copytruncate`, e o serviço continuou `active`.

O `logrotate.timer` está `enabled`, com a próxima execução à meia-noite UTC.

## Saída

```text
Fri 2026-10-30 00:00:00 UTC  20h Thu 2026-10-29 03:10:14 UTC      - logrotate.timer logrotate.service

```

## Decisões

- `copytruncate` em vez de `create`: o arquivo é mantido aberto pelo `systemd`,
  e a alternativa seria reiniciar os três serviços toda noite.
- `maxsize 10M` além de `daily`: durante os testes de carga da fase 10 um log
  pode crescer mais que o normal em poucas horas.
- `rotate 7`: uma semana, que cabe folgado em 1 GB com logs comprimidos.

## Problemas e pendências

A primeira versão do arquivo tinha a diretiva `su appsvc appsvc`, e a execução
falhou com:

```text
error opening /mnt/atividade3-logs/memory/app.log: Permission denied
```

A causa: `su` faz o `logrotate` **descartar** os privilégios e rodar como
`appsvc`, mas o `app.log` é criado pelo `systemd` como `root` (o processo baixa
de privilégio depois de abrir o arquivo). Com `copytruncate`, o `logrotate`
precisa **ler e truncar** esse arquivo, e `appsvc` não pode. A diretiva foi
removida: o `logrotate` roda como root, tem acesso ao arquivo e não baixa
privilégio. As permissões de arquivo no volume continuam `0640 root:root`, que é
o esperado para log de serviço.
