# T10.2 — Envio do monitor para a VM

**Data (UTC):** 2026-10-29T05:29:58Z
**Fase:** 10 — medições de carga
**Status:** concluída
**Evidência:** `evidencias/T10.2-monitor-upload.txt` · `T10.2-monitor-upload.png`

## Objetivo

Deixar na VM o monitor de recursos que acompanha cada execução de carga, no
mesmo diretório das aplicações (`/opt/atividade3/scripts`).

## Comandos executados

```bash
# na VDI, com o script do repositório
cat scripts/monitor.py | ssh ... ubuntu@150.165.85.77 \
  'sudo install -d /opt/atividade3/scripts &&
   sudo tee /opt/atividade3/scripts/monitor.py >/dev/null &&
   sudo python3 -m py_compile /opt/atividade3/scripts/monitor.py &&
   echo "sintaxe ok" && wc -l /opt/atividade3/scripts/monitor.py'
```

## O que aconteceu

O `tee` gravou o arquivo pelo `stdin` do SSH, que é o caminho que funciona sem
precisar de chave privada na VDI nem de `scp` autenticado à parte. Antes de
declarar sucesso, o `python3 -m py_compile` compilou o arquivo **dentro da VM**:
se a transferência tivesse truncado o script, o `py_compile` acusaria erro em vez
de deixar um monitor quebrado para a fase seguinte.

## Saída

```text
sintaxe ok
119 /opt/atividade3/scripts/monitor.py
```

## Decisões

- Instalar em `/opt/atividade3/scripts`, ao lado de `/opt/atividade3/apps`
  criado na T5.2, em vez de mandar o arquivo para o `$HOME` do `ubuntu`:
  todo o deploy fica em um lugar só e some junto se a VM for recriada.
- Compilar depois de copiar: a T10.3 depende de 13 execuções seguidas do
  monitor, e descobrir um erro de sintaxe na primeira delas custaria a matriz
  inteira.
- Usar `tee` sobre SSH em vez de `scp`: o usuário `ubuntu` entra por uma chave
  que fica na VDI, e o `sudo` de destino já está disponível pelo mesmo canal.

## Problemas e pendências

Nenhum.
