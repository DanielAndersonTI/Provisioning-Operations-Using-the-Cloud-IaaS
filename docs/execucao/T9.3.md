## Objetivo

Conferir que o snapshot terminou utilizável e que a VM e o volume continuaram
intactos depois de tirá-lo — ou seja, que a operação foi **não destrutiva**.

## Comandos executados

```bash
openstack image show snap-vm-daniel-ranya -c id -c name -c status -c size \
  -c disk_format -c min_disk -c properties
openstack image list -f yaml
openstack server show vm-daniel-ranya -c name -c status
openstack volume show vol-daniel-ranya-logs -c name -c status -c attachments
```

## O que aconteceu

| Conferência | Resultado |
| --- | --- |
| status da imagem | `active` |
| formato | `qcow2` |
| tamanho | `1983840256` bytes ≈ 1,85 GiB |
| `image_state` | `available` |
| `stores` | `rbd` |
| projeção na lista de imagens | presente com o ID `7fb6d24c-...` |
| VM depois do snapshot | `ACTIVE` |
| volume depois do snapshot | `in-use`, anexado em `/dev/vdb` à VM `bdc0447e-...` |

O `min_disk` de 20 GB é a mesma projeção do disco do flavor, herdada da imagem
base; o `size` é o tamanho **real** da imagem em disco, bem menor que os 20 GB
porque o sistema de arquivos só tem o que foi escrito.

A lista completa de imagens mostra o snapshot convivendo com as imagens base e
com os snapshots dos outros grupos, sem colisão de nome — cada um tem o seu
prefixo.

## Decisões

- Conferir também o **servidor e o volume**, e não só a imagem: o risco de um
  `server image create` é justamente deixar a VM parada em algum estado de
  pausa, e a atividade continua depois disso.
- Usar `openstack image list -f yaml` em vez de filtrar colunas: o cabeçalho
  `Disk Format` tem espaço e quebra a lista de colunas na linha de comando.

## Problemas e pendências

Nenhum. O snapshot está `active`, a VM segue `ACTIVE` e o volume segue anexado.
