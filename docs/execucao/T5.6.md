# T5.6 — Logs iniciais das aplicações

**Data (UTC):** 2026-10-29T03:16:21Z
**Fase:** 5 — deploy das aplicações
**Status:** concluída
**Evidências:** `evidencias/T5.6-app-logs.txt` · `T5.6-app-logs.png`

## Objetivo

Confirmar que cada serviço escreve no próprio arquivo de log, e que o arquivo é
do usuário `appsvc` — sem isso, o volume da fase 6 não teria o que guardar.

## Comandos executados

```bash
ssh ... ubuntu@150.165.85.77 'sudo sh -c "ls -l /var/log/atividade3/*/"
    sudo tail -n 5 /var/log/atividade3/{cpu,memory,io}/app.log'
```

## O que aconteceu

Cada perfil tem o seu `app.log` e cada um registrou a linha de inicialização com
a porta e o limite de concorrência que o código define:

```text
==> /var/log/atividade3/cpu/app.log <==
cpu application listening on port 8000 (max 32 concurrent work units)

==> /var/log/atividade3/memory/app.log <==
memory application listening on port 8001 (max 4 concurrent work units)

==> /var/log/atividade3/io/app.log <==
io application listening on port 8002 (max 16 concurrent work units)
```

O limite aparecer na própria linha de log é útil na hora de interpretar os
testes de carga da fase 10: acima desses valores o tempo de resposta cresce
porque o servidor enfileira, não porque a rede piorou.

Nesta fase os logs ainda estão em `/var/log/atividade3/<perfil>/app.log`. A
fase 7 muda o destino para o volume, e a T7.3 mostra o mesmo arquivo já no
`/mnt/atividade3-logs`.

## Saída

```text
cpu application listening on port 8000 (max 32 concurrent work units)
memory application listening on port 8001 (max 4 concurrent work units)
io application listening on port 8002 (max 16 concurrent work units)
```

## Decisões

- Um arquivo por perfil, em vez de um log único: facilita a rotação e isola a
  leitura durante os testes.
- `append:` em vez de `journal`: o `journal` grava em `/var/run`, que é tmpfs e
  sumiria no reboot; com `append:` o log é um arquivo comum, que pode morar no
  volume.

## Problemas e pendências

A primeira captura do `ls -l` falhou com `No such file or directory`, porque o
curinga `/var/log/atividade3/*/` era expandido pelo shell do usuário `ubuntu`
antes do `sudo` — e `ubuntu` não tem permissão de leitura nesse diretório
(`0750 appsvc`). A captura foi refeita com `sudo sh -c "ls -l ..."`, que resolve
o curinga já como root.
