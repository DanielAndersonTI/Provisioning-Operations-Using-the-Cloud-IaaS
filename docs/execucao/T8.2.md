# T8.2 — Listeners, pools, monitores e membros das aplicações

## Objetivo

Publicar as três aplicações na VIP do `poi-atividades`, cada uma na sua porta, com
verificação de saúde em HTTP.

## Comandos executados

Para cada perfil (`cpu`, `memory`, `io`), com `ext` = porta externa e `int` =
porta interna:

```bash
openstack loadbalancer listener create --name app-<perfil>-daniel-ranya \
    --protocol HTTP --protocol-port <ext> poi-atividades
openstack loadbalancer pool create --name pool-app-<perfil>-daniel-ranya \
    --lb-algorithm ROUND_ROBIN --listener app-<perfil>-daniel-ranya --protocol HTTP
openstack loadbalancer healthmonitor create --name hm-app-<perfil>-daniel-ranya \
    --delay 5 --timeout 4 --max-retries 3 --type HTTP --url-path /health \
    --expected-codes 200 pool-app-<perfil>-daniel-ranya
openstack loadbalancer member create --name vm-daniel-ranya \
    --subnet-id 17de9c72-e5dc-4da0-ae0a-013f7e42400e --address 10.5.9.15 \
    --protocol-port <int> pool-app-<perfil>-daniel-ranya
```

## O que aconteceu

A topologia ficou assim:

| Aplicação | Listener (VIP) | Pool | Membro | Health check |
| --- | --- | --- | --- | --- |
| cpu | `app-cpu-daniel-ranya` : 8100 | `pool-app-cpu-daniel-ranya` | `10.5.9.15:8000` | `GET /health` 200 |
| memory | `app-memory-daniel-ranya` : 8101 | `pool-app-memory-daniel-ranya` | `10.5.9.15:8001` | `GET /health` 200 |
| io | `app-io-daniel-ranya` : 8102 | `pool-app-io-daniel-ranya` | `10.5.9.15:8002` | `GET /health` 200 |

A porta externa é diferente da interna porque a VIP é **compartilhada**: se eu
usasse 8000/8001/8002 na VIP, colidiria com outro grupo na mesma porta. O Octavia
traduz a porta no amphora.

O monitor é HTTP em `/health` com `delay 5`, `timeout 4` e `max-retries 3`, e
espera exatamente `200`. Um monitor TCP aprovaria o membro mesmo com a aplicação
travada mas com o socket aberto; o HTTP em `/health` só põe o membro `ONLINE`
quando o processo responde de verdade. O `expected-codes 200` também é
deliberado: sem essa restrição, um `503` de sobrecarga contaria como saudável.

Os três membros ficaram `ONLINE`, cada um na porta interna certa:

```text
== pool-app-cpu-daniel-ranya
| vm-daniel-ranya | 10.5.9.15 | 8000 | ONLINE |
== pool-app-memory-daniel-ranya
| vm-daniel-ranya | 10.5.9.15 | 8001 | ONLINE |
== pool-app-io-daniel-ranya
| vm-daniel-ranya | 10.5.9.15 | 8002 | ONLINE |
```

O script é idempotente: antes de cada `create` ele consulta se o objeto já existe
e pula. Isso importa porque o LB responde `HTTP 409 is immutable` quando outro
grupo está aplicando uma mudança e a criação precisa ser repetida — repetir sem
essa checagem acabaria criando duplicatas quando a resposta chegasse tarde.

## Saída

```text
| name                     | provisioning_status | operating_status |
| app-cpu-daniel-ranya     | ACTIVE              | ONLINE           |
| app-memory-daniel-ranya  | ACTIVE              | ONLINE           |
| app-io-daniel-ranya      | ACTIVE              | ONLINE           |
```

## Decisões

- Um listener por aplicação, e não um listener com regras L7: cada aplicação é um
  serviço separado, com porta própria e health check próprio.
- Monitor HTTP em `/health`, com código esperado 200.
- Script idempotente com nova tentativa em 409, por causa do LB compartilhado.

## Problemas e pendências

A primeira execução falhou na criação do listener de io com

```text
Load Balancer 57c2b14a-... is immutable and cannot be updated. (HTTP 409)
```

Além disso o script, nessa versão, não repetia: as criações seguintes de pool,
monitor e membro de io falharam em cascata com `Unable to locate ...`. Duas
correções: repetição com espera de 15 s entre tentativas para o 409 de
imutabilidade, e verificação de existência por nome do objeto — inclusive do
health monitor, que precisa ser consultado por `hm-app-<perfil>-daniel-ranya` e
não pelo nome do pool.
