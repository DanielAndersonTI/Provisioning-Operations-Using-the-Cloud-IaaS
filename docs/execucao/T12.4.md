# T12.4 — Matriz tamanho do trabalho × concorrência

**Data (UTC):** 2026-10-29T15:51–16:10Z
**Fase:** 12 — correções da revisão e medições complementares
**Status:** concluída
**Evidências:** `T12.4-size-{cpu,memory,io}-s<size>-c<conc>` (27 pares `.txt`/`.png`), `results/summary-size.csv`, `results/summary.csv`

## Objetivo

Medir, para cada perfil, como o custo do trabalho pedido muda a vazão e a
latência com um, dois e quatro clientes. Os cenários base da fase 10 usam um
único tamanho por perfil; aqui cada perfil tem três tamanhos, o que permite
separar "mais clientes" de "pedido maior".

| Perfil | Tamanhos | Concorrências |
| --- | --- | --- |
| CPU-bound | 5, 10, 20 | 1, 2, 4 |
| Memory-bound | 16, 32, 64 | 1, 2, 4 |
| IO-bound | 512, 1024, 4096 (KiB) | 1, 2, 4 |

São 27 execuções de 30 s, cada uma com 5 s de aquecimento descartados e
amostragem de recursos de 0,5 s dentro da VM.

## Comandos executados

O laço é o mesmo para todas as combinações; o de CPU, como exemplo:

```bash
for tamanho in 5 10 20; do
  for conc in 1 2 4; do
    id="size-cpu-s$tamanho-c$conc"
    curl -s "http://150.165.85.77:8100/metrics" > /tmp/before-$id.json
    ssh ... "python3 /opt/atividade3/scripts/monitor.py --scenario $id \
             --seconds 35 --interval 0.5 --out /tmp/mon-$id.csv" &
    python3 scripts/load_test.py --url "http://150.165.85.77:8100/work?size=$tamanho" \
        --level $conc --concurrency $conc --duration 5  --run-id "warmup-$id" ... >/dev/null
    python3 scripts/load_test.py --url "http://150.165.85.77:8100/work?size=$tamanho" \
        --level $conc --concurrency $conc --duration 30 --run-id $id ...
    wait
    ssh ... "cat /tmp/mon-$id.csv" > results/resources-v2-$id.csv
    curl -s "http://150.165.85.77:8100/metrics" > /tmp/after-$id.json
    python3 scripts/app_metrics.py /tmp/before-$id.json /tmp/after-$id.json \
        $id results/app-metrics.csv
  done
done
```

## O que aconteceu

Vazão bem-sucedida (req/s) vista pelo cliente, por tamanho e concorrência:

```text
perfil   tamanho   c=1     c=2     c=4
cpu       5       2,97    7,67   16,68
cpu      10       5,47   12,48   19,19
cpu      20       6,24    8,57    9,28

memory   16      13,07   31,47   33,21
memory   32       8,72   12,11   25,50
memory   64       7,22    9,74   14,14

io      512       5,46    8,16   10,54
io     1024       4,63    2,48    2,02
io     4096       2,09    2,11    2,49
```

O tempo de trabalho medido **dentro** do servidor (`/metrics`, somando o tempo
entre entrar e sair da vaga) cresce com o tamanho, como esperado:

```text
perfil   tamanho   trabalho médio (ms), c=1     c=4
cpu       5               41,9                  61,5
cpu      10               67,9                 149,4
cpu      20              102,3                 315,4

memory   16                5,4                   5,1
memory   32               46,2                  44,9
memory   64               74,0                  94,1

io      512              123,4                 314,7
io     1024              159,8                1987,6
io     4096              437,6                1623,5
```

Leitura dos números:

- **CPU**: o trabalho cresce quase linearmente com o tamanho (41,9 → 67,9 →
  102,3 ms para 5/10/20 com um cliente). Com quatro clientes o mesmo trabalho
  fica 1,5 a 3 vezes mais lento (149 ms para tamanho 10), porque quatro threads
  disputam um único vCPU: a vazão para de crescer entre 16 e 19 req/s.
- **Memória**: o salto está entre 16 e 32 — 5,4 ms contra 46 ms de trabalho. A
  alocação é feita em blocos, então o tamanho 16 cabe numa alocação pequena e o
  32 já entra na faixa seguinte. Por isso o tamanho 16 é o mais barato dos três,
  mesmo tendo mais requisições por segundo.
- **IO**: é o perfil em que o tamanho mais pesa. Com 1024 KiB o trabalho por
  requisição chega a 2 s com quatro clientes, e a vazão cai de 10,5 (512 KiB)
  para 2,0 req/s. O `iostat` da mesma janela mostra o disco do volume em 76 %
  (512 KiB), 90 % (1024 KiB) e 89 % (4096 KiB) de ocupação — o gargalo é o
  número de operações de escrita do volume, não a CPU da VM, que fica em 1 a 4 %.

## Decisões

- **Uma repetição por ponto da matriz.** A matriz serve para mostrar tendência,
  não para estimar precisão; a dispersão entre repetições foi medida à parte, nos
  nove cenários base (T12.6), onde a mesma célula foi executada três vezes.
- **Vazão de sucesso separada da vazão total.** No perfil de IO o cliente às
  vezes recebe erro de leitura de resposta por timeout do próprio `load_test`;
  contar só o 2xx evita inflar a vazão com requisições que não completaram.
- **Trabalho medido no servidor, além da latência do cliente.** Os dois números
  contam histórias diferentes: a latência do cliente inclui o caminho
  VDI → balanceador → VM, que é de ~55 ms fixos (ver T12.6).

## Problemas e pendências

- **Cauda de 1,2 s no perfil de CPU com tamanho 5.** O p95 desse cenário fica em
  ~1195 ms mesmo com mediana baixa: o cliente na VDI às vezes espera um ciclo
  inteiro de 1,2 s por um pacote. É artefato do caminho até a nuvem, não do
  servidor — o tempo de trabalho medido no servidor nesse mesmo cenário é de
  41,9 ms.
- **Ordem de execução fixa.** O primeiro cenário de cada perfil paga o custo de
  aquecer o cache do sistema; por isso o aquecimento é descartado e a matriz é
  lida como curva, não como valor absoluto de cada ponto.
